# GPU 2D流体爆炸/火焰 —— 兼容性与性能预算调研报告

## 0. 结论速览(TL;DR)

1. **WebGL2 + EXT_color_buffer_float 在2024-2026年覆盖率约95-98%**,可以放心作为流体模拟的门槛条件;不建议做WebGL1(OES_texture_half_float)回退实现——增量收益薄(约1-3个百分点,且多半集中在本来就更容易在别的地方翻车的老设备上),但要写一整套并行的shader/精度/NPOT适配代码。**检测不过直接落到现有的序列帧/粒子爆炸(v6)方案即可**,这不是"降级到残废",而是"退回到你们已经做好、用户已经拍板的东西"。
2. **关键项目专属发现(比任何通用网络数据都重要)**:实测本项目安装的 Phaser 4.2.1(`node_modules/phaser`)源码/构建产物里,主渲染器**始终请求 `canvas.getContext('webgl', ...)`,整个 4.2.1 构建包里没有任何一处 `getContext('webgl2')`**。也就是说 Phaser 自己的游戏画布上下文是 **WebGL1**,不是 WebGL2。流体模拟**必须在项目自建的独立 WebGL2 上下文/canvas 里跑**,不能假设能直接"借用" `this.game.renderer.gl` 拿到浮点渲染目标能力。这决定了整个技术方案的骨架,详见第3节。
3. **192×108 / 256×144 网格 + ~8 pass + 20 次压力迭代,这套预算就是全网被引用/fork最多的 WebGL 流体 demo(PavelDoGreat/WebGL-Fluid-Simulation)一字不差的标准管线**(curl→vorticity→divergence→pressure clear→**pressure jacobi×20**→gradient subtract→advect velocity→advect dye,共8类pass、实际27次全屏draw call/实例/帧),而且那个demo的模拟网格默认还比我们的256×144小(128基准),同时它还额外跑一个更贵的1024级"染色场"高分辨率层——这套budget比一个已证明能在手机上流畅跑的demo更省。**在192×108~256×144这个尺度下,性能瓶颈根本不是像素量或ALU,而是draw call/状态切换的固定开销**;192 vs 256 之间的性能差异是噪声级别(大概率<1-2ms),该按视觉效果选,不必因为性能纠结分辨率。
4. **局部模拟域(锚定爆炸点、~600px世界区域)明显优于全屏场**,尤其适合本项目(960×540基准画布、相机变焦范围只有0.97-1.07、爆炸都是钉在关卡里的静态道具触发)。
5. **气瓶连锁反应(2-3个)应该共用一块场,不要各开一块**——因为成本是按draw call数(即"pass数×实例数")线性增长,不是按像素;3个独立场=3倍draw call(约81次),叠加在本来就是全场最忙的物理/粒子高峰时刻,风险远大于分辨率选择本身。共场还有额外好处:后引爆的气瓶会被先前热浪/气压场自然扰动,读起来更真实,不是纯粹的性能妥协。
6. 提供了兜底降档阶梯与判定代码要点,见第7、8节。

## 1. WebGL2 + EXT_color_buffer_float 覆盖率(2024-2026)

用了两套方法论不同、互相印证的数据源:

**方法论A —— caniuse(按全球浏览器版本市占加权的"usage"口径)**
- `EXT_color_buffer_float`(WebGL2下渲染到float/half-float颜色附件的扩展):**全球usage 94.67%**。Chrome 56+(2016)、Firefox 51+、Safari **15+(2021年9月起)**、Edge 79+、Samsung Internet 6.2+、Chrome/Firefox for Android 均已支持。iOS/Safari 15是最后补齐的一块,2026年时间点上这已经是5年前的事了。

**方法论B —— web3dsurvey.com(真实设备遥测口径,按"已经具备该能力的设备"统计)**
- WebGL2 总体支持率:约**97-98%**(Windows 99.03% / Android 98.74% / iOS 97.02% / Mac 96.95% / ChromiumOS 99.83% / **Linux 90.56%明显偏低**)。同时标注"7.77%的WebGL2上下文报告 major performance caveat"——即**能创建上下文但是软件渲染(SwiftShader等)、事实上不能用**,这是和"支持率"完全独立的另一个风险维度,必须单独判定(见第8节)。
- `EXT_color_buffer_float`(条件于"已经有WebGL2"):约**99.9%+**,也就是说只要设备有WebGL2,这个扩展幾乎必然跟着有,不是额外的独立瓶颈。

两套口径合起来的结论:**"WebGL2 + 能渲染到float/half-float纹理"覆盖了全球大约95-98%的用户**,methodology gap(94.67% vs 97-98%)基本就是"到底有多少人还在用WebGL2以下的浏览器"这一件事本身的度量误差,不影响结论。

> 口径说明:web3dsurvey的具体小数位是通过工具抓取其页面文本得到的,该站数据本身是JS动态渲染,抓取存在一定噪声风险;但caniuse的94.67%是完全独立的另一套统计源,两者数量级一致(94-98%),可以放心采信"高95%区间"这个结论,不必纠结具体小数点。

**剩下的约3-6%由什么构成:**
- 真·无WebGL2(老旧Linux发行版、极老iOS、企业锁定的老浏览器)——约2-4%;
- "支持"但被判定 major performance caveat(黑名单驱动/软渲染/云主机远程桌面等)——WebGL1和WebGL2都有约7-8%这个比例,**这批人即使扩展查询全部通过,实机也跑不动**,必须靠 `failIfMajorPerformanceCaveat` 主动拦截,不能只查扩展列表;
- **中国市场专属、任何国际统计都测不到的风险**:360/QQ/搜狗等双核浏览器,"极速模式"=Chromium内核(现代、没问题),"兼容模式"=IE Trident内核(可被企业策略强制,也有用户手动切换的)。**Trident内核基本没有可用的WebGL2**,IE11时代的WebGL1支持也残缺不全。这部分无法从caniuse/web3dsurvey这类国际数据里量化,只能定性提示:**上线后应该用真实的可用性打点(而不是先验估计)来看"落到序列帧"的用户里有多大比例是这类双核浏览器兼容模式触发的**,这比继续查国际统计更有信息量。
- 另外,**4399自己公布的最低配置门槛是 Windows 7/8/10/11 + Pentium 4级CPU + 2GB内存 + 集成显卡即可**——这个门槛本身老到夸张(奔四是2010年前的CPU),说明平台愿景上是覆盖非常老旧的机器的,即便现实中真正还在用奔四的人已经绝迹,这也是一个信号:**测试矩阵里必须包含"入门集显笔记本/多年不换的教室/网吧电脑"这一档**,不能只在自己的开发机上测。

**结论**:用 `WebGL2 + EXT_color_buffer_float + failIfMajorPerformanceCaveat` 三件套做门槛,是2024-2026年这个时间点上性价比最高的判定线。

## 2. WebGL1(OES_texture_half_float)回退到底值不值得做

数据:
- WebGL1 总体设备支持率与 WebGL2 几乎同一量级(约97-98%),说明"有WebGL1但没有WebGL2"其实是一个很薄的人群切片(大概2-4个百分点),而不是一大块独立市场。
- 该切片里,再叠加 `OES_texture_half_float`(创建/采样半浮点纹理)+ `EXT_color_buffer_half_float`(渲染到半浮点framebuffer,WebGL1/WebGL2都适用的独立扩展)+ `OES_texture_half_float_linear`(双线性过滤,advection效果必需)三个条件同时成立,web3dsurvey给出的 `EXT_color_buffer_half_float` 总体支持率约98.86%,**但分平台看 Android 只有90.28%,明显偏弱**——这正是WebGL1时代出了名的"扩展列表里有,但framebuffer实际渲染时`checkFramebufferStatus`返回不完整"的重灾区(旧Mali-400/PowerVR SGX类GPU与老驱动的典型坑),需要跑时二次校验而非只看`getExtension()`是否返回非null。
- 综合下来:**为WebGL1单独实现一整套半浮点流体管线,大概只能多救回1-3个百分点的用户**,而且这批用户本身设备更弱、更容易在别的地方(比如drawcall开销、内存)也吃力,体验上限也更低。换来的代价是:GLSL ES 100 vs 300、没有原生`RGBA16F`只能靠扩展常量、NPOT纹理限制处理、无MRT只能拆更多pass、独立的能力探测/QA矩阵——工程量不小,且和本项目"临时凑合最多一轮"的制作哲学冲突(等于主动做了一个更容易在实机上翻车的"半成品兜底")。

**建议:不做WebGL1流体回退。** 判定只走"WebGL2+扩展+性能caveat"这一条线,任何一项不达标——包括纯WebGL1设备、纯Canvas设备(Phaser AUTO兜底的最后一层)、或"性能caveat"命中——统一回落到**现有的序列帧/粒子爆炸系统(v6,2026-07-25已定版)**。这不是牺牲这部分用户的体验,而是让他们保留"这个功能上线前本来就有"的、用户已经认可的效果,零工程债。

## 3. 项目专属关键发现:Phaser 4.2.1 主上下文其实是 WebGL1

这是本次调研里唯一不能从任何通用网络资料查到、必须读本项目实际安装的包源码才能确认的事实,直接决定架构落点:

```
node_modules/phaser/src/renderer/webgl/WebGLRenderer.js:709
gl = canvas.getContext('webgl', config.contextCreation) || canvas.getContext('experimental-webgl', config.contextCreation);
```

在构建产物 `node_modules/phaser/dist/phaser.esm.js`(Vite实际会加载的文件)里,`grep getContext('webgl2'` **命中0次**——整个包里没有任何地方请求过WebGL2上下文,包括其内部的能力探测工具(`Device.Features`)也是同样请求`'webgl'`。也就是说:**不管Phaser 4这个大版本名义上带来了多少新特性(RenderNode/SpriteGPULayer/Filters等),4.2.1这个具体安装的小版本,给游戏主画布创建的就是一个WebGL1上下文**(其内部注释显示它是靠在WebGL1上手动挂一堆扩展,模拟出部分WebGL2能力的"效果",而不是真正切到WebGL2)。

**架构含义**:
1. 流体模拟不能指望"在Phaser自己的gl里加一个渲染节点就完事",因为那个gl实例本身不满足`RGBA16F`可渲染的前提(Phaser自己的`WebGLTextureWrapper.js`里也确实找不到任何`HALF_FLOAT`/`RGBA16F`的踪迹,印证它的纹理管线是按8-bit格式设计的,不是为float走线的)。
2. 正确做法是:**自建一个完全独立的 `<canvas>` + `getContext('webgl2', {failIfMajorPerformanceCaveat:true})`**,整套ping-pong FBO模拟(速度/温度/燃料/压力场)都在这个独立上下文里跑,和Phaser的WebGL1上下文互不干扰(避免手工插入的draw call污染Phaser内部缓存的状态假设——纹理单元绑定/当前program/blend模式等,这类跨"外来代码"和"引擎自身状态机"共享一个context的坑,是WebGL集成里最容易被引擎升级悄悄改状态管理方式而回归的雷)。
3. 最终结果如何喂回Phaser画面,两个可行方案:
   - **(a) 独立DOM canvas叠加**:一个透明背景的`<canvas>`,每帧根据爆炸世界坐标算出的相机变换,更新它的CSS `transform`(和scene-fx-pipeline技能里"HUD root容器按`1/zoom`补偿"是同一套数学,只是作用对象从Phaser容器换成DOM元素),交给浏览器合成器去做layer混合——不需要任何像素拷贝,最省,但天然脱离Phaser的深度排序体系(适合"爆炸永远画在最上层/UI下面"这种简单遮挡关系)。
   - **(b) 每帧`texImage2D(canvas)`上传成Phaser纹理**:让合成后的火焰精灵作为普通Phaser GameObject参与深度排序(能和跳箱/立柱等前景遮挡物正确前后穿插时更自然),代价是每帧多一次canvas→texture的拷贝(多数浏览器实现是GPU-side blit,但不同驱动组合下有隐性同步的可能,需要用项目自己已有的"renderer.snapshot + rAF step 测墙钟"方法实测,不能假设)。
   - 由于本项目"障碍物边界"这条需求(火焰/烟雾不能穿墙)本身应该在**模拟内部**用一张障碍物遮罩纹理(0/1,静态solids栅格化一次即可,爆炸生命周期内关卡几何不变,不需要逐帧重绘)去约束速度场/压力场边界条件来实现,和"喂回Phaser画面"是两件独立的事,不要混为一谈。

如果之后要落地实现,**第一步验收动作就应该是拿这两行代码去chrome-devtools MCP里实测`renderer.gl instanceof WebGL2RenderingContext`确认这个判断在当前环境下依然成立**(以防未来升级Phaser小版本改变了这个行为)。

## 4. 192×108 / 256×144 网格 + ~8 pass + 20次压力迭代:真实GPU成本量级

### 4.1 与"最著名的开源demo"对照

用来对标的是全网被fork/引用最多的浏览器流体demo——**PavelDoGreat/WebGL-Fluid-Simulation**(GitHub描述直接写"works even on mobile",也是Google Experiments收录的那个)。读取其`script.js`源码,一次`step(dt)`严格按这个顺序跑:

1. Curl(涡量计算)
2. Vorticity(涡量约束力施加)
3. Divergence(散度)
4. Pressure clear(压力场清零)
5. **Pressure Jacobi迭代 ×20**(`PRESSURE_ITERATIONS: 20`是它的默认值)
6. Gradient subtract(压力投影)
7. Advect velocity(速度场平流)
8. Advect dye(染色/密度场平流)

——**这就是用户问题里"~8 pass、压力迭代20次"的原始出处**,不是拍脑袋的估算,是这个demo一字不差的标准管线(不含它额外的bloom/sunrays/display这些纯展示层可选特效)。换算成实际draw call数:1+1+1+1+**20**+1+1+1 = **27次全屏quad绘制/实例/帧**。

关键的是它的默认分辨率:`SIM_RESOLUTION: 128`(速度/压力/散度/涡量这些"模拟"用的网格,按画布长宽比缩放,在16:9画布上大约128×72≈9216 texel,**比我们提议的192×108/256×144还小**),但它把"看得见的染色场"单独拆到`DYE_RESOLUTION: 1024`(约1024×576≈59万texel,**比我们的方案大一个数量级还多**)去跑高分辨率advection+渲染。也就是说:**这个已经证明能在手机上流畅跑60fps的demo,其最贵的部分(百万级texel的染色场advection+display)比我们提议的"速度场和可见燃料/温度场统一在192-256级别"的方案贵得多**。我们的预算是在一个已验证安全的框架下,选了一个更保守（更省）的档位。

### 4.2 具体量级计算

- 192×108 = 20,736 texel;256×144 = 36,864 texel(比192×108多78%纹理量)。
- 27个pass,每个texel平均约4-5次双线性依赖纹理采样(邻域采样,Jacobi/散度/梯度这类stencil运算的标准开销)+个位数ALU op:
  - 192×108档:约**300万次纹理采样/帧**,千万级ALU op/帧;
  - 256×144档:约**550万次纹理采样/帧**。
  - 60fps下换算成"吞吐率"是每秒1.8亿~3.3亿次纹理采样——这个数量级对任何2013年之后出厂的GPU(包括入门集显,比如Intel HD 4000往后)都只是其纹理吞吐能力的极小零头(入门集显的纹理填充率普遍在十亿到数十亿texel/秒量级),**纯计算/带宽层面完全不是瓶颈**。
- **真正的瓶颈是draw call/状态切换的固定开销**,不是像素量:每次切FBO+program+清屏在WebGL里都有一次命令校验+驱动翻译的隐性税(Windows下Chrome/Edge/Firefox都通过ANGLE转译到D3D11,这层翻译本身有开销),经验量级大约零点几毫秒/draw call。27次draw call,悲观情况下大约1-4ms,现代浏览器+正常驱动下通常远低于1ms。
- **结论:192×108 与 256×144 之间的性能差异是噪声级别的**(两者都远低于16.6ms预算,差异大概率在1-2ms以内甚至更小),**应该按火焰边缘的视觉颗粒度来选分辨率,不必为了省性能纠结这两个档位**。真正影响预算的维度是"pass数量"和"并发实例数",不是网格边长。

### 4.3 一个值得顺手借鉴的技巧

Pavel的demo把"模拟分辨率"和"可见染色场分辨率"拆成两个不同网格(低分辨率算物理,再用双线性采样把结果喂给一个更精细的染色场做advection+渲染),专门用来解决"火焰边缘不规则、不像马赛克"这种视觉诉求——如果192-256级别的flame轮廓看起来还是偏"方块感",可以只把**燃料/温度这个可见标量场**单独提到2倍分辨率(比如速度场256×144、可见场512×288),压力solve(最贵的20次循环)依然留在低分辨率不变——这样能改善边缘自然度,而不需要把最贵的部分也翻倍。这是可选的精细化手段,不是必须项。

## 5. 局部模拟域(跟随爆炸的~600px窗口) vs 全屏场

结合本项目实际情况判断(960×540基准画布、相机变焦范围仅0.97~1.07、爆炸源都是关卡里的静态道具/固定命中点,不是持续移动的火源):

**局部窗口域(锚定爆炸点的~600px世界区域)——推荐**
- 成本恒定,不随镜头缩放/平移变化(纯粹是一个跟随世界坐标摆放的普通quad,自动继承相机变换,跟HUD那套"1/zoom补偿"完全不相关,因为它活在世界空间不是屏幕空间)。
- 同样的网格预算下,**texel密度明显更高**:600px窗口用256×144网格,约2.34世界px/texel;如果同一网格铺满960px全屏,约3.75世界px/texel——局部窗口在同预算下清晰度高出约60%。
- 没有火/烟的时候可以整条~27-draw pipeline直接跳过(CPU侧一个"当前有无存活爆炸实例"的标志位即可判断,不需要读回GPU状态),不会有"全屏场哪怕没人炸也要一直跑"的常驻开销。
- 障碍物遮罩只需要栅格化这一小块窗口内的solids,可以在爆炸触发那一刻算一次就够(关卡静态几何在爆炸~1-2秒生命周期内不会变),不需要逐帧重绘。
- 缺点:需要给窗口留够余量(预期最大烟雾/火焰半径之外再留一圈),并在边界做柔和衰减(密度场在接近窗口边缘时提前平滑归零),否则烟雾扩散会撞到一堵看不见的"墙";另外这套设计天然不适合"持续移动的火源"(比如一路燃烧滚动的物体),但**本项目的爆炸场景(气瓶/弹药/RPG命中点)都是空间上钉住的单点事件**,这个限制基本不影响使用。真要支持移动火源,标准解法是"按整数texel平移窗口+清空/重灌被让出来的边缘条带"(scrolling/toroidal技巧),而不是重新分配网格。

**全屏/满视口场**
- 优点:永远不会有边界问题,任意数量/任意位置的同屏爆炸自动共享同一张场,烟雾理论上可以飘出任意远。
- 缺点:必须常驻覆盖整个可视区域,**哪怕全场没有任何火,也要按同样网格持续跑那~27个pass**(除非同样加一个"无活跃爆炸就跳过"的开关,但那样等于把局部方案的开销控制手段又实现了一遍,却仍然背着"要更大网格才能达到同等清晰度"和"清晰度随镜头缩放漂移"这两个全屏方案独有的缺点)。

**结论**:局部窗口域是明显更适合本项目的选择,用户原本的设计方向是对的。

---

## 6. 多发爆炸并发(气瓶连锁2-3个):共用一场 vs 各开一场

因为第4节已经确认**成本主要由"draw call数=pass数×实例数"决定,不是像素量**,这里答案很直接:

- **各开一场**:3个气瓶连锁 = 3 × 27 ≈ **81次全屏draw call/帧**,而且这恰好发生在游戏本来就最忙的时刻(连锁爆炸=物理碎块横飞+粒子+震屏+可能的敌人反应同时触发),是最不该额外加负担的节点。
- **共用一场**:只要几个气瓶的爆炸中心落在同一个局部窗口的合理覆盖范围内(连锁反应定义上彼此距离就很近,通常远小于~600-900px的窗口尺度),把窗口开大到能同时覆盖它们的并集,多个起爆点各自往同一张场里"注入"一次冲量/燃料(对应demo里的`splatProgram`,一次很小的额外draw call),总开销依然是**约27次左右**(+几次小splat),而不是乘以爆炸数。
- **额外的好处不只是省性能**:共用同一个压力场意味着后引爆的气瓶会被先前那团热浪/气压场自然推挤、变形——两团火焰读起来是"在互相影响的同一片空气里",比两个互不知道对方存在的独立火球叠在一起更真实,这是白得的视觉提升,不是纯粹的妥协。

**具体规则建议**:
- 全局维护一个很小的并发场实例上限(比如**2**,对应"绝大多数爆炸是孤立事件,连锁是唯一的多发场景"这个设计前提)。
- 新爆炸触发时,先判断其位置是否落在某个存活场的覆盖半径(或距离阈值)内——落在内就往那个已有场里注入,不新开;不在范围内且还没到实例上限,才新开一块;如果已经到上限且离所有存活场都太远,**直接退回到序列帧/粒子爆炸(v6)**处理这一发——这与"能力不达标→回落序列帧"复用同一条代码路径,只是触发条件从"设备不支持"换成了"预算超限",概念上是一件事的两种触发方式。

## 7. 兜底降档阶梯

按"省下的开销 / 损失的视觉质量"性价比从高到低排列(前面几档几乎不影响观感,越往后越明显,与第4节"压力solve是最贵、也最值得先砍的部分"的结论一致):

| 档位 | 动作 | 依据 |
|---|---|---|
| T0 满配 | 256×144,压力迭代20,涡量约束开,局部场并发上限2 | 默认档,已验证远在预算内 |
| T1 | 网格降到192×108 | 省约44%texel/带宽,视觉几乎无损(仍高于Pavel demo的128基准) |
| T2 | 压力迭代 20→8-10 | 压力solve是最贵的循环(占27个draw call里的20个),是单项杠杆最大的一刀;代价是流体不可压缩性略变差,对~1-2秒的短命特效基本不影响观感 |
| T3 | 关闭涡量约束(vorticity confinement) | 直接砍掉curl+涡量施加两个pass;失去内部翻卷的湍流细节,火焰变得更"顺滑"但依然是一个真实档位,不是破损档位 |
| T4 | 并发场上限降到1 | 连锁反应之后全部强制合并进同一张场/排队 |
| T5 兜底 | 直接切回序列帧/粒子爆炸(v6) | 能力门槛不达标(无WebGL2/无扩展/`failIfMajorPerformanceCaveat`触发/运行时`webglcontextlost`)时的唯一去处,也是T0-T4全部降到底仍然扛不住时的最终退路 |

**档位选择机制建议**:不要去猜测/识别具体GPU型号(脆弱且涉及指纹隐私限制),而是复用本项目已有的"rAF真实墙钟测帧时"方法论——开局或首次爆炸时跑一小段真实帧,measure `performance.now()`增量,超预算就降一档,**只降不升**(同一局游戏内避免来回震荡),并把选定档位存起来(GameState或localStorage),下次爆炸/下次进入关卡直接沿用上次已知安全档位,不必每次重新试探。

## 8. 检测不支持 → 回落序列帧:判定代码要点

核心原则:**用自建的独立WebGL2上下文探测,不要假设能从Phaser的`renderer.gl`直接拿到(第3节已证实Phaser 4.2.1主上下文是WebGL1)**;`failIfMajorPerformanceCaveat`拦截软渲染;`getExtension`之外还要实际建一次float framebuffer校验`checkFramebufferStatus`(扩展"查得到"和"这个格式真的能渲染"在部分老设备/驱动上是两回事);运行时还要挂`webglcontextlost`兜底。

```js
function detectFluidCapability() {
  const probe = document.createElement('canvas');
  probe.width = probe.height = 4;

  let gl;
  try {
    gl = probe.getContext('webgl2', {
      failIfMajorPerformanceCaveat: true, // 拒绝黑名单驱动/SwiftShader软渲染
      antialias: false,
      depth: false,
      stencil: false,
      alpha: true,
    });
  } catch (e) {
    return { ok: false, reason: 'context-creation-threw' };
  }
  if (!gl) return { ok: false, reason: 'no-webgl2-or-perf-caveat' };

  const ext = gl.getExtension('EXT_color_buffer_float');
  if (!ext) return { ok: false, reason: 'no-float-render-target-ext' };

  // 扩展存在 !== 这个具体格式真的可渲染,老设备上这两者会脱节,必须实测一次。
  const tex = gl.createTexture();
  gl.bindTexture(gl.TEXTURE_2D, tex);
  gl.texImage2D(gl.TEXTURE_2D, 0, gl.RGBA16F, 4, 4, 0, gl.RGBA, gl.HALF_FLOAT, null);
  const fbo = gl.createFramebuffer();
  gl.bindFramebuffer(gl.FRAMEBUFFER, fbo);
  gl.framebufferTexture2D(gl.FRAMEBUFFER, gl.COLOR_ATTACHMENT0, gl.TEXTURE_2D, tex, 0);
  const status = gl.checkFramebufferStatus(gl.FRAMEBUFFER);
  gl.deleteFramebuffer(fbo);
  gl.deleteTexture(tex);

  if (status !== gl.FRAMEBUFFER_COMPLETE) {
    return { ok: false, reason: 'rgba16f-fbo-incomplete' };
  }

  return { ok: true, gl }; // gl 这里只是探测用的临时上下文,正式模拟另建一个
}

// 建议在 BootScene 里跑一次并缓存结果 + 挂运行时上下文丢失兜底:
const fluidCap = detectFluidCapability();
GameState.fluidEnabled = fluidCap.ok;

if (fluidCap.ok) {
  simCanvas.addEventListener('webglcontextlost', (e) => {
    e.preventDefault();
    GameState.fluidEnabled = false; // 运行中途也能优雅退回序列帧,不崩溃
  }, false);
}

// 所有爆炸触发点统一走:
function spawnExplosion(x, y, kind) {
  if (GameState.fluidEnabled && fluidBudget.canAllocateOrMerge(x, y)) {
    fluidExplosion(x, y, kind);
  } else {
    spriteExplosion(x, y, kind); // 现有v6方案,零改动复用
  }
}
```

要点提炼:
- 探测上下文与正式渲染上下文**分开**(探测完可以留着复用,也可以扔掉重建,但逻辑上要允许"探测通过≠这就是要用的那个上下文",给未来切换实现留余地)。
- `failIfMajorPerformanceCaveat` 是目前判定"是否软渲染"最标准、且不涉及指纹隐私争议的手段(相比之下`WEBGL_debug_renderer_info`/`UNMASKED_RENDERER_WEBGL`在Firefox的`resistFingerprinting`等隐私设置下可能被屏蔽或返回泛化字符串,不可靠,不建议作为主判据,最多做辅助日志)。
- `EXT_color_buffer_float`覆盖了16F和32F两种精度;本项目按用户给定的RGBA16F需求,这一个扩展够用,不需要再额外判`OES_texture_float_linear`(那是32F的线性过滤,16F的线性过滤在WebGL2里是核心特性自带的,不需要扩展)。
- 一定要做**运行时**的`webglcontextlost`兜底,不是只在启动时判一次就完事——真实设备上GPU进程崩溃/驱动重置/移动端切后台唤醒都会触发这个事件,不接住会直接白屏或抛异常。
- 预算超限(第6节的并发场上限)复用同一个"回落序列帧"出口,让"能力不支持"和"资源超预算"变成同一条代码路径的两个触发条件,而不是两套独立逻辑。
