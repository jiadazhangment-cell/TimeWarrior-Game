### 4️⃣ 超级大炮 supercannon(slot 4)— In2 锚:Blaster(+ DanTheGun 后座)

### ⚠️ 切枪延迟 —— 我们完全没有,这是 ② 的最大缺口

**In2 证据**:`SwitchWeapon()`(`Hero.as:2745-2828`)每个 case 都写 `reloading = N`,而 `PrepareShot()` 的门槛就是 `reloading >= 0` → **切枪冷却与开火冷却复用同一个计时器,谁写得晚谁说了算**。这是极省事的设计,值得移植。

In2 各枪切入锁定帧 → ms(×33.33):

| In2 武器 | 帧 | ms | 出处 |
|---|---|---|---|
| pistol | 21 | 700 | `Hero.as:2770` |
| smg | 22 | 733 | `Hero.as:2776` |
| blaster | 25 | 833 | `Hero.as:2782` |
| grenade | 20 | 667 | `Hero.as:2788` |
| smg2 | 28 | 933 | `Hero.as:2794` |
| antitank | 35 | 1167 | `Hero.as:2800` |
| double_pistol | 35 | 1167 | `Hero.as:2810/2816` |

**我的建议**:
1. `weapons.json` 每把枪补 `switchDelayMs`;`WeaponSystem.handleSelect()` 末尾加一行
   `this.nextShotAt = Math.max(this.nextShotAt, now + w.switchDelayMs)`
   —— 直接复用现有 `nextShotAt` 字段,即 In2"一个计时器两用"的语法,不要新建状态机。
2. **数值压缩到 In2 的约 1/2.5**:步枪 **200** / 霰弹 **300** / RPG **420** / 大炮 **520** ms。
   理由:In2 667~1167ms 的切枪硬直放在我们更快的节奏(TTK 460ms vs In2 400ms、重力 2.35×)里会明显卡顿;但**保留"越重的枪掏得越慢"的排序**,这才是 In2 真正的设计意图。
3. 抄 In2 的一个反直觉事实:**切枪延迟与开火冷却互相独立**(grenade 掏枪 20 帧却要 50 帧才能再开一枪;smg2 掏枪 28 帧但 3 帧一发)。**不要写成 `switchDelay = fireInterval × k` 的公式。**

## ③ 弹药模型建议

**我们现状**:**完全没有弹药系统**(已核:`src/` 全域无 ammo 逻辑,`prop_ammo2/3/ammochest` 只是场景装饰贴图)。

**In2 用什么**(证据):
- **按弹药类型共享池,不是每枪一个弹匣**:`Hero.as:3064` `GetAmmo` 走 `ammo_pack[weapons[id].ammo_type]`
- **手枪真无限**:`AddWeapon(WPN_PISTOL,"pistol",0,0,10,0,true)` max_ammo=0,且 `ShotPistol()`(`Hero.as:2092-2121`)**全函数无任何 GetAmmo/AddAmmo 调用**
- **跨武器共池是刻意的**:`AddWeapon(WPN_GRENADE,"grenade",4,...)` 与 `AddWeapon(WPN_ANTITANK,"antitank",4,...)` **同为 ammo_type=4** → 榴弹与反坦克抢同一份"爆炸物资源"
- **池上限分档**:速射高、重武器低 —— 手枪∞ / 双枪60 / SMG **500** / Blaster **40** / 爆炸类 **40** / 双管 **500**
- **无过热、无弹匣装填动画**:通读全部 7 个 Shot 函数,只有"弹药检查 + reloading 帧计数"两件事
- **打光自动切枪**:`NoAmmoAutoSwitchWeapon()`(`Hero.as:618-648`)按 `power` 值最接近原则挑一把还有弹的顶上 + `snd_empty` + "depleted" 浮字

**我的建议(倾向 In2,逐条给理由)**:

| 决策 | 建议 | 理由 |
|---|---|---|
| 总模型 | **共享池 + 起手枪无限**,照抄 In2 | 简单、可存档(就是一个数组)、无弹匣状态机 |
| 步枪 | **无限弹药**(承担 In2 手枪的兜底角色) | In2 的安全网设计:"打光了也永远有枪可用"。4399 单局闯关里,弹尽=卡关的挫败远大于资源管理的乐趣 |
| 霰弹枪 | 独立池,上限 **40** | 对应 In2 Blaster/爆炸类的 40 档 |
| **RPG + 超级大炮共享一个"重弹药池"** | 上限 **12** | **这是 In2 最值得移植的单一想法**(grenade+antitank 共 ammo_type=4)。它制造真实的"这发到底给火箭还是留给大炮"张力,零额外代码成本。⚠️ 若不想要这层取舍,退化成两个独立池即可,不影响其它设计 |
| 过热/装填动画 | **不做** | In2 确认没有;我们也不需要 |
| HUD | 当前枪弹药**原始数字**,不做弹匣/备弹拆分 | In2 `World.as:1511` 直接渲染池原始值 |
| 打光自动切枪 | **做**,但候选包含 slot 1 | In2 `NoAmmoAutoSwitchWeapon` 遍历**从下标 1 开始、故意跳过 0 号槽**(报告2标为动机不明)。我们步枪就在 slot 1 且无限弹,直接让它做兜底目标即可,不用复刻那个怪癖 |

> ⚠️ **绝对不要照抄这一行**:`Hero.as:3018` `ammo_pack[weapons[param1].ammo_type] += 16;` —— 该函数体**完全没有使用传入的 `param2`**,永远固定 +16。而所有调用点都明确传递增减量(开火 `AddAmmo(WPN_SMG,-1)`、双管 `-2`、拾取传正数)。四份报告独立标记、我亲自复核原文确认一致。**判定为 FFDec 类反编译器对已优化 SWF 的寄存器误读**(照字面执行会导致"每开一枪弹药 +16",与游戏公认表现直接矛盾)。**实现按调用点意图写 `pool += param2`。**

## ④ RPG 抛射体实现要点(照抄 In2 的哪些机制)

按"抄 / 已有 / 别抄"三分:

### ✅ 必抄(我们现在没有)

**A. 分层爆炸:内圈伤害 + 外圈只推不伤**
- In2 证据:`Grenade_2.as:139-141` `param1=120`(伤敌)、`param3=240`(纯击退),经 `World.CreateExplosion(x,y,r,force,dmg,dmg_hero,filter,pushRadius,pushFilter)` 传入;`Explosion.SetPushRadius()`(`Explosion.as:319-327`)在伤害圈外**再建一个更大的纯物理圆形碰撞体**;力度线性衰减 `Explosion.as:292` `push.Multiply(force * root.limit(1 - (d - r)/(push_r - r), 0, 1))` —— 从内圈边缘满力线性衰减到外圈边缘归零。
- 落地:`Explosives.applyBlast()` 增加 `pushR` 参数,在现有 `for (const b of s.gibs.getBodies())` 循环外再加一轮对敌人/尸块的"只推不伤"结算,权重用上面那条线性公式。**这是把 RPG 从"一个伤害圆"升级成"有体积感的冲击波"的关键一步。**

**B. 自伤单开一个更小的圈**
- In2 证据:`Grenade_2.as:141-142` **两次独立 `CreateExplosion`** —— 第一次半径 120 打敌人(filter 排除玩家),第二次半径 **65** 只对玩家生效。
- 落地:`applyBlast` 里玩家判定改为 `Math.hypot(...) < r * (opts.playerBlastRadiusFactor ?? 1)`。当前 `Explosives.js:136` 玩家与敌人共用同一个 `r`。

**C. 伤害不对称**
- In2 证据:玩家手雷 `Hero.as:1877` 传 `(...,19,60,10,Grenade.TYPE_HERO,...)` → 伤敌 60 / 自伤 10 = **6:1**;敌方手雷 `Enemy.as:1121` 传 `(...,19,20,20,Grenade.TYPE_ENEMY,...)` → **20:20 = 1:1**。**同一个类、同一个构造函数,数值刻意分叉** = 偏袒玩家是设计而非疏漏。
- 落地:`blastDamagePlayer` 24 → **16**。

**D. 屏震"弱不压强 + 硬顶"规则**
- In2 证据:`World.as:6403` `if(param1 < shake_amplitude){ return; }`(比当前正在进行的震动弱就直接丢弃),`World.as:6407` `shake_amplitude = limit(param1 + shake_amplitude, 0, 30)`(叠加但硬顶 30)。
- 落地:我们 `Explosives.js:123` 已有**距离衰减**(In2 没有,我们更好),但缺"弱不压强"。在 camera shake 消费端加这条规则,防止连环爆炸时小震抢大震的戏。
- In2 屏震强度谱供标定:手雷爆 **12**、英雄摔死 **7**(`Hero.as:523/2998`)、Boss 大招 **15~20**(`ACEBoss.as`)、硬顶 **30**。

### ✅ 已有,确认正确别动

**E. 射程到点强制自爆** —— In2 `AntitankShot.as:159-164` 累计飞行 >900 强制爆;我们 `WeaponSystem.js:164` `if (r.traveled > r.w.range) { this._detonate(...) }` **已是同款** ✅
**F. 直击伤害与爆炸伤害分开结算** —— In2 `Hero.as:1741` antitank 直击 40 + 爆炸 splash 10 两笔账;我们 `WeaponSystem.js:141` `takeHit(r.w.damage,...)` 后再 `_detonate` **已是同款** ✅
**G. 逐帧扫掠线段命中而非点检测** —— In2 `AntitankShot.Step()`(`AntitankShot.as:107-165`)每帧推进一段再对该段 `RaycastOne`;我们 `WeaponSystem.js:129` `segVsRect` 逐帧扫掠 **同构** ✅

### ❌ 别抄

**H. In2 antitank 的零重力纯直线** —— 我们要"火箭筒"读感,轻微下坠(140)比绝对直线更有操作纵深。
**I. In2 antitank 命中不震屏** —— 通读 `AntitankShot.as` 全文无 `root.Shake` 调用(报告3、4 一致)。这是基准的留白/疏漏,不是可取之处;我们照常震。

## ⚠️ 不确定 / 存疑事项(如实标注)

1. **`AddAmmo` 的 `+= 16`**(`Hero.as:3018`):原文属实(我逐字复核),但与全部调用点意图矛盾。判定为反编译失真,**无法静态 100% 证伪**。建议按调用点意图实现。
2. **`reloading` 换算 ±1 帧**:`PrepareShot` 的 `reloading >= 0` 门槛推出"N+1 帧",但 `--reloading` 与开火检查在同一帧内的先后顺序未逐帧验证。所有 ms 值精度 ±33ms。
3. **伤害 ×2.33 系数**:基于 In2 `Enemy.as:102` 的**类默认值 30** 与我们唯一敌人巡逻机兵 70。In2 关卡可逐实例覆写敌人 HP(`Enemy.as:1316`),故 30 是"标准杂兵"锚而非全局锚。我们后续加高血量敌人时该系数需重新校准。
4. **距离取 1:1 而非 ×1.22**:依据是移速精确 1:1(In2 360px/s = 我们 360px/s),但角色身高是 1.22×(72 vs 88)。两个尺度不自洽是 In2 与我们美术比例的固有差异。若实际试玩觉得爆炸圈"看起来偏小",按 1.22× 上浮到 blastRadius 146 是有依据的备选。
5. **`Beam` 穿透性纠正的边界**:我确认了射线掩码只含 `COLLIDE_BRICKS + COLLIDE_STOP_BEAM` 且盒体掩码含 `COLLIDE_ENEMIES`,但未逐帧运行验证多敌人同时结算的实际表现。结论置信度高但非运行时实证。
6. **In2 30fps 结论的范围**:`timeStep = 1/30` 是**物理步长**且每帧 Step 一次,渲染帧率写在 FLA/SWF 头里(不在 .as 中)。若 SWF 头是 60fps 而每帧仍 Step 1/30,则物理会跑成 2 倍速——这在 Flash 游戏里极罕见,但严格说未能排除。所有 ms 换算基于"渲染帧率 = 物理帧率 = 30"。
7. **后座单位换算**:`owner.velocity.x -= 10` 中 `velocity` 的单位由 `max_horizontal_speed = 12` 与我们 maxSpeed 360 的吻合反推为 px/帧,属**间接推断**,非直接证据。
8. **`Harpoon` 归属**:全库找不到 `hero.harpoon = new Harpoon(...)` 赋值,仅 `Exoarmor_2.as` / `Danmaku.as` 构造。英雄抓钩在这份构建里大概率未接线。不影响本设计表。
